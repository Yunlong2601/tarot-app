# Pin the spread, ink the links, earn each flight

ShenTarot's "Mystical & Editorial" direction does not need a showpiece website to copy. No single reference combines dark parchment, editorial serif type and connected-card explanations, so the direction has to be put together from three proven sources. **The Public Domain Review** and the **London Review of Books** supply the reading typography: asymmetric margin grids, small-caps ledes and old-style figures. **The Pudding's sticky-scrollytelling pattern** (with Scrollama) keeps the spread pinned while the interpretation scrolls. **FLIP-style measured flights** (Paul Lewis, GSAP Flip, Flutter Overlay) move a card from the deck to its exact slot. The current build already has the hardest signature parts: a split-and-riffle fan, a glowing middle card, a lift-then-fly into slots that respects the Celtic Cross rotation, and a flip reveal. Its gaps are in robustness and access, not spectacle. Reading the code turned up four problems. The fan exposes **one semantic button that always draws the middle card**, with no per-card keyboard focus. Reduced motion checks only `MediaQuery.disableAnimations`, which according to the Flutter API docs does not follow **iOS Reduce Motion**. The question is **held only in memory** (`AppState.draftQuestion`). The press-and-hold "keep shuffling" timer reshuffles every 900 ms, which is spectacle rather than meaning. The recommended direction is a desktop "Folio" layout: sticky spread on the left, numbered explanations on the right, joined by one hairline ink line. It collapses on the phone to a pinned thumbnail strip plus a numbered list. Evidence is uneven, and the report keeps it separate: nothing below was verified by running a demo in a browser. "Inspected" means HTML or CSS source was fetched and grepped, "documented" means taken from official docs or a README, and "inferred" means my own synthesis. The only award that could be verified is **Tarot-o-bot's 2019 Awwwards Site of the Day (score 7.3, with its lowest sub-score, 6.33, for accessibility)** ([Awwwards](https://www.awwwards.com/sites/tarot-o-bot)).

## Measured geometry, not decoration, makes the editorial feel work

### Layout and typography: asymmetric tracks with literary details

*Reference → principle.* The PDR `3fr 7fr 3fr` system and LRB's small-caps lede share one idea: whitespace and typographic detail do the work that chrome and colour would otherwise do. Together they suggest ShenTarot should be a narrow serif measure with wide asymmetric margins, where the margins hold metadata such as the numeral, arcana and position name.

*Implementation (web, inferred from the inspected CSS).* Named lines express the same ratio and add a full-bleed lane for spreads:

```css
.folio { display:grid; grid-template-columns:
  [full-start] minmax(1rem,1fr) [margin-start] 3fr [text-start] 7fr [text-end] 3fr [margin-end] minmax(1rem,1fr) [full-end]; }
.folio .lede::first-line { font-variant: small-caps; letter-spacing:.04em; }
.folio p { font-variant-numeric: oldstyle-nums; } h1,h2 { text-wrap: balance; }
.card-edge-label { writing-mode: vertical-lr; } /* Jen Simmons pattern: numeral up the card edge */
```

*ShenTarot adaptation (Flutter).* `lib/app/theme.dart` already sets Baskerville as `displayFont` and uses flatter radii (4–8). Add `fontFeatures: [FontFeature.oldstyleFigures()]` to `bodyMedium`/`bodyLarge`, and a `labelSmall` style that uses `FontFeature.enable('smcp')` where the font supports it, falling back to uppercase with 0.08em tracking. Whether Baskerville on iOS ships `smcp`/`onum` has not been checked, so test it. For the future web build, bundle one free serif on both platforms; Alegreya is proven at PDR. Matching type everywhere matters more than the specific family. Phone layouts use one column, following LRB's collapse to `column-count: 1`. *Tradeoff:* asymmetric margins waste width on small laptops. Fall back to `1fr 5fr 1fr` below about 1100 px.

### Layering and masking: fades instead of frames

PDR softens scroll edges with `mask-image: linear-gradient(180deg, transparent 0, #000 1.75rem, #000 calc(100% - 1.75rem), transparent)` instead of borders ([PDR](https://publicdomainreview.org)). Flutter's equivalent is a `ShaderMask` with a vertical `LinearGradient` and `BlendMode.dstIn` around the reading scroller and the card fan. It gives a fade-at-the-margin feel without boxes. Parchment grain should be **one static texture layer** under content, not a filter applied per widget. Avoid `BackdropFilter` on scrolling surfaces; `showAppDialog` already blurs behind dialogs, which is the right place for blur.

### Transforms and travel: one measured flight per card

The FLIP principle is to measure inside the roughly 100 ms after input, then animate only `transform`/`opacity` ([aerotwist](https://aerotwist.com/blog/flip-your-animations/)). The current `_onPick` in `lib/features/draw/draw_screen.dart` already follows it. It reads the slot `RenderBox`, derives the slot's rotation with `atan2(m.entry(1,0), m.entry(0,0))` (the Celtic Cross crossing card), inserts a `FlyingCard` `OverlayEntry`, and lands on completion. This is the Flutter analogue of GSAP Flip reparenting into a rotated container. Keep it. Two refinements are worth making. Use `MaterialRectCenterArcTween`-style arcing, the same curve family as `Hero` ([Flutter docs](https://docs.flutter.dev/ui/animations/hero-animations)), so the path reads as "laid down by a hand" rather than a straight slide. And measure the slot rect **before** removing the card from the fan, so a layout shift from the fan shrinking cannot move the destination. Use `Hero` with a `flightShuttleBuilder` only for placed card → full card-detail route.

### Pointer, keyboard, touch and focus: the fan needs per-card semantics

The reference demos document no keyboard model at all, so this part is ShenTarot's own design (inferred). Today `DeckFan` wraps the whole fan in one `Semantics(button, excludeSemantics: true, onTap: _pickMiddle)`. Screen-reader users can therefore only ever take the middle card, and keyboard users on a desktop or web build cannot browse. The fix keeps touch exactly as it is and adds a focus model:

```dart
// deck_fan.dart: roving focus over the arc; drag stays optional.
Shortcuts(
  shortcuts: const {
    SingleActivator(LogicalKeyboardKey.arrowRight): _MoveIntent(1),
    SingleActivator(LogicalKeyboardKey.arrowLeft):  _MoveIntent(-1),
    SingleActivator(LogicalKeyboardKey.enter):      ActivateIntent(),
    SingleActivator(LogicalKeyboardKey.space):      ActivateIntent(),
  },
  child: Actions(actions: {
    _MoveIntent: CallbackAction<_MoveIntent>(onInvoke: (i) {
      setState(() => _focused = (_focused + i.delta).clamp(0, shown.length - 1));
      _spinTo(_focused);                      // rotate arc so focused card is centred
      HapticFeedback.selectionClick();
      return null;
    }),
    ActivateIntent: CallbackAction(onInvoke: (_) => _pick(_focused, ...)),
  }, child: Focus(autofocus: isDesktop, child: fan)),
)
// Semantics: increasedValue/decreasedValue let VoiceOver/TalkBack swipe-adjust the focused card.
Semantics(label: tr('Deck, {0} cards', [n]), value: tr('Card {0} of {1}', [_focused+1, n]),
  onIncrease: () => _move(1), onDecrease: () => _move(-1), onTap: () => _pick(_focused, ...))
```

Keep the existing "tap the deck to draw the next card" as the simple path, labelled visibly as **"Draw for me"**, so motor-impaired users are never forced to browse.

### Animation state and cancellation: one explicit state machine

The current guard (`if (_flying != null || _drawn.length >= _spread.cardCount) return;`) and the synchronous `_remaining.remove(pick.deckIndex)` already block double-picks during flight. That matches the recommendation to consume the card id before the animation starts. Make the implicit states explicit, `idle → shuffling → browsing → lifting → flying → placed → revealing → complete`, in one enum, so that every button's `onPressed` derives from it. Wrap the flight in `controller.forward().orCancel` with a `TickerCanceled` catch that calls `land()`. A disposed or interrupted flight then still commits the card to its slot and never loses it. `dispose()` already removes the overlay. On the web, the equivalents are `el.getAnimations().forEach(a => a.cancel())` before a new WAAPI flight, or `Flip.killFlipsOf`. Do not use View Transitions for card moves, because "only one view transition is allowed to run at a time" and a new one snaps the old to its end ([Chrome for Developers](https://developer.chrome.com/docs/web-platform/view-transitions/same-document)). Reserve them for page-level reading → card-detail changes.

### Reduced motion: check both flags, keep the spatial story

Flutter's `MediaQueryData.disableAnimations` follows Android's "Remove animations". **iOS Reduce Motion is exposed separately** as `AccessibilityFeatures.reduceMotion` ([Flutter API](https://api.flutter.dev/flutter/widgets/MediaQueryData/disableAnimations.html)). Every reduced-motion check in the app (`motion.dart`'s `_reduced`, `deck_fan.dart`'s `_reduceMotion`, `draw_screen.dart`, `_EmptySlot`) reads only the first flag. On the primary platform, iPhone, those users therefore get the full riffle and flight. Add one helper and use it everywhere:

```dart
// lib/app/motion.dart
bool reduceMotion(BuildContext c) =>
    MediaQuery.maybeDisableAnimationsOf(c) == true ||
    View.of(c).platformDispatcher.accessibilityFeatures.reduceMotion;
```

Chrome's guidance is that reduced motion "doesn't mean the user wants *no motion*" ([Chrome for Developers](https://developer.chrome.com/docs/web-platform/view-transitions/same-document)). So under reduced motion, replace the flight with a 150 ms cross-fade into the slot (the slot highlight is still visible), the riffle with a single "deck settles" fade, and the flip with an instant face swap plus a name announcement. Do not simply `land()` with no feedback, which is what happens today.

## Every surface gets one editorial gesture and a standard contract

The common principle in this section is to put expressive styling on top of a boring, standard interaction contract. APG explicitly uses disclosure buttons, **not `role="menu"`**, for site navigation ([APG](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/)). The editorial flourish never changes the keyboard model underneath.

**Navigation and disclosures.** Reference: APG disclosure navigation and the APG modal dialog ([APG dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)). Principle: Escape closes and returns focus to the trigger; a full-screen menu traps Tab. On desktop web, the left margin carries a "Contents" disclosure whose indicator is a 1 px rule rotating 90° instead of a chevron. On the phone, a full-screen "folio" index lists items as large Baskerville lines with a hairline rule between each, opened by `showGeneralDialog` (the route scopes focus, and pop returns it). In Flutter, wrap toggles in `Semantics(expanded: open, button: true)` and pad hit areas to 44 pt even when the visible word is thin. Codrops' line-by-line menu reveals are by the author's own description proofs of concept ([Codrops](https://tympanus.net/codrops/2021/07/28/layout-with-reveal-animations-and-content-preview), search snippet only). Borrow the 40 ms-per-line stagger and drop it under reduced motion. *Tradeoff:* a text-only index reads beautifully but scans more slowly than icons. Keep the bottom tab bar on phone and use the folio only for secondary destinations.

**Search with illustrated results.** References: the APG combobox, [Fuse.js](https://www.fusejs.io/) (Apache-2.0, typo-tolerant Bitap, about 6.8–8.6 kB gzipped) and [cmdk](https://github.com/pacocoursey/cmdk) (MIT) for the anatomy: Input, List, Group, Empty, Loading. Principle: focus stays in the input, and the highlighted option uses `aria-activedescendant`, which the script must scroll into view itself. Results are a ruled index, not tiles. Each row has a 40×68 thumbnail with `alt=""` (the name is the label), the name in serif, and "Major Arcana · V" in small caps. The selected row is marked by a 2 px gold margin rule rather than a filled pill. Index aliases ("Pope" for The Hierophant) and upright/reversed keywords. For 78 cards a small Dart Levenshtein or trigram scorer is enough; no package is needed. The empty state echoes the query: *No card called "hierphnt". Did you mean The Hierophant? · Browse the Major Arcana*. Flutter's `SearchAnchor` is full-screen by default only on mobile ([Flutter API](https://api.flutter.dev/flutter/material/SearchAnchor-class.html)). Use it on the phone, and on desktop use `RawAutocomplete` with a custom `optionsViewBuilder`. The existing `lib/features/cards/cards_browser.dart` is the natural home. *Tradeoff:* thumbnails cost decode time, so pre-size them and cache.

**Question input and reflection writing.** References: GOV.UK Character count, whose count appears near the limit, **never blocks typing** and announces politely ([GOV.UK](https://design-system.service.gov.uk/components/character-count/)); iA Writer Focus Mode, which "highlights the sentence or paragraph you're working on and fades everything else" ([iA](https://ia.net/writer)); and Apple HIG's advice to offer curated starter suggestions for open-ended inputs ([Apple HIG](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/generative-ai.json)). The question field becomes a ledger line: an underline-only border, a visible "Your question" eyebrow, and a hint ("Open questions work best…") that stays visible instead of living in a placeholder. Starter chips insert text only when tapped. The counter appears past about 85 % and turns oxblood when over, without enforcing `maxLength`. Reflection uses a 60–70ch column with optional iA-style fading of non-current paragraphs. **Protect against a lost question.** `setDraftQuestion` currently only assigns a field. Persist it, debounced at about 800 ms, to `shared_preferences` keyed by reading, restore it with a "Discard draft" option, and show "Saved to this device · 14:02" in the margin. Use `RestorableTextEditingController` in `ask_screen.dart` so the text survives process death. *Tradeoff:* a persisted question is private data on the device, so clear it when the reading is saved or abandoned.

**Card browsing, selection, correction and orientation.** Are.na's grid **and table** views for calm, feed-free browsing ([Are.na](https://www.are.na/about)) suggest a "Plates / Index" two-option toggle for the 78 cards. Plates is a captioned image grid with thin rules; Index is a ruled table of numeral, name, arcana and keywords, which suits Codrops LinesToLayout's row-to-preview expansion. For scanned readings, orientation and correction belong in `lib/features/scan/orientation_dialog.dart` and `card_picker_screen.dart`. Per APG, a toggle's **label must not change with its state** ([APG Button](https://www.w3.org/WAI/ARIA/apg/patterns/button/)). Use a stable "Reversed" toggle (`Semantics(toggled: …)`) or an Upright/Reversed radio pair, paired with a small card glyph rotated 180° and the word in small caps. Never signal the state with gold alone. "Change card" is a text button with an ink underline and an Undo snackbar, not an icon. *Tradeoff:* explicit text costs space on small cards, so put correction controls below the card, not on it.

**Button states.** References: the Codrops LineHoverStyles pseudo-element underline (MIT, [repo](https://github.com/codrops/LineHoverStyles)) and GOV.UK's high-contrast focus approach ([GOV.UK](https://design-system.service.gov.uk/get-started/focus-states/)). Hover draws an ink underline from the left over 350 ms. Press is "letterpress": a 1 px downward shift and an inset shadow, with no colour flash. Focus is a double ring, a 2 px ink outline plus an outer soft-gold band, so contrast comes from the ink (aim for ≥3:1 against parchment, which still needs measuring) and the brand comes from the gold. In Flutter, build this as a single `ButtonStyle` in `theme.dart` using `WidgetStateProperty.resolveWith` over `hovered`/`pressed`/`focused`/`selected`, with `RoundedRectangleBorder(borderRadius: BorderRadius.zero)` for primary actions. Pair it with a `MouseRegion`-driven underline `CustomPainter` for text links. The letterpress press state is my own synthesis; no published design-system component was found.

**Connected-card explanations.** The full pattern is in the layout section below. The rule is that **lines are decoration and the relationship lives in text**. Each explanation is headed "3 · The Tower — crossing" and includes "Related: 1 · The Star" as a real link. The SVG or `CustomPainter` overlay is `aria-hidden`/`ExcludeSemantics`. Chrome notes that anchor positioning creates no semantic relationship and that `aria-details` support "is still developing" ([Chrome](https://developer.chrome.com/blog/anchor-positioning-api)).

**A clearly labelled future AI companion (concept only, not a feature).** References: GOV.UK's phase banner (a tag plus one plain line) ([GOV.UK](https://design-system.service.gov.uk/components/phase-banner/)); Apple HIG's "Clearly identify when and where you use AI" and its instruction to communicate that output "may contain errors" ([Apple HIG](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/generative-ai.json)); PAIR's warnings against "AI magic" hype and against first-person language implying near-human understanding ([PAIR](https://pair.withgoogle.com/chapter/mental-models/)); Carbon's AI label with an explainability popover ([Carbon](https://carbondesignsystem.com/guidelines/carbon-for-ai/)); and iA Writer showing AI-generated text in a distinct colour ([iA](https://ia.net/writer)). The concept card carries a `CONCEPT · NOT YET AVAILABLE` small-caps tag in a 1 px ink border. Carbon's glow is deliberately rejected because it clashes with restrained gold. The headline is "A reading companion, powered by AI", with no human name or face; a role name such as "Margin Notes" is acceptable. The card then has three short columns: what it would do (reflect your journal back, suggest questions, explain symbolism); what it won't do (predict events, advise on medical, legal or financial matters, replace your interpretation; "It can be wrong"); and "Your words stay yours" (AI text set in a distinct ink, editable and discardable). Interest is collected with an unchecked "Tell me when it's ready" checkbox and a permanent "Not interested". Avoid the mystic first person ("I sense…"). Since ShenTarot already generates AI readings, apply the same honest label to the existing reading sections too. The concept page should not be the only place where AI is disclosed.

## The draw ritual works when every motion commits a real state change

The signature sequence is choose spread → shuffle → browse or pick → travel → reveal → interpret. The test for each beat is the one from the card-interaction research: choreography reads as intentional when it **represents real state change** and as decorative when it loops or blocks input to no purpose. Measured against that test, the current build is about 80 % of the way there.

**Placement geometry.** The current normalised layouts are correct in shape. Horseshoe is an inverted-V arc of seven slots (0.08,0.88 → 0.5,0.12 → 0.92,0.88). Celtic Cross puts its cross at x≈0.24 and the staff at x=0.8, from 0.88 rising to 0.13. Two precise rules should be written into data rather than left implicit. First, **Celtic position 2 lies across position 1 at 90° with a higher z-order**, and in the reading it should be offset by about 8 % of card height so position 1 remains tappable. Today both share `Offset(0.24, 0.5)`, so on touch one card fully covers the other. Second, the staff reads **bottom to top (7 → 10)**, so the "next position" highlight climbs, which teaches the spread's logic. The five-card cross uses `_cross5` (left, centre, right, top, bottom); keep its numbering visible because its reading order is not spatially obvious.

```
Horseshoe (7)                Five-card cross             Celtic Cross (10)
        4                           4                     5          10
     3     5                     1  2  3                4 [1┼2] 6     9
   2         6                      5                     3          8
 1             7                                                     7
```

**Duplicate, redraw and lost-question protection.** Duplicates are already structurally impossible: the card is removed from `_remaining` synchronously, and taps are ignored while `_flying != null`. Keep that, and add a test asserting that 78 rapid taps produce `cardCount` unique cards. Redraw protection exists partly: "Shuffle again" is disabled once `placed > 0`. Leaving the draw screen with 1 ≤ placed < n should ask "Leave this reading? The cards you've drawn will be returned to the deck." using `PopScope(canPop: placed == 0 || allPlaced)`. A "New reading" control after completion also needs a confirmation. The lost-question fix is the persistence described above, plus displaying the question at the top of the draw screen as an editable line rather than truncated `titleMedium` text, so users can see what they are asking.

**Meaning versus spectacle.** Meaningful motion: the real reshuffle, the card leaving the fan (state: consumed), the flight ending in a numbered slot (state: assigned to a position), and the flip with its orientation (state: revealed). Spectacle that should stay brief, skippable and off under reduced motion: the middle-card glow, tilt, the constellation loader, and any particles. The 900 ms auto-reshuffle loop is the one spectacle that currently masquerades as meaning, because users cannot tell whether "more shuffling" changes anything. Make it one honest action instead.

## Three compositions, one recommendation: the Folio

All three proposals share the same tokens (parchment ground, ink text, gold used only for *state*, hairline rules) and the same DOM/semantics order: the spread as an ordered list of positions, followed by explanations in the same order.

**A. Folio (sticky spread with ink annotations).** This follows the Pudding/Scrollama sticky-side layout plus Copes-style line drawing. On desktop, a two-column grid (`minmax(320px,44%) 1fr`, 4rem gap) pins the spread on the left. The explanation in the viewport-middle band (IntersectionObserver `rootMargin: '-45% 0px -45% 0px'`) becomes active, and a single hairline joins its number to the card. Related cards get fainter secondary lines. The benefit is that you never lose sight of the spread while reading. The limit is that lines need per-frame re-measurement, and it collapses awkwardly on narrow screens without a mobile variant.

```
┌──────────────────────────────────────────────────────────────┐
│ SHENTAROT            Celtic Cross · "What should I see…?"  ⌕ │
├───────────────────────┬──────────────────────────────────────┤
│  5        10          │  III · THE CROSSING                  │
│4 [1┼2] 6   9  ◀───────┼──③ The Tower, reversed               │
│  3         8          │   Upheaval held back…                │
│            7          │   Related: 1 · The Star              │
│  (sticky)             │  IV · THE ROOT ……                    │
└───────────────────────┴──────────────────────────────────────┘
```

**B. Plate index (archive-first).** This follows PDR's margins and LinesToLayout's row index. The reading is a numbered list of plates. Each row has a large Baskerville name, a small-caps position, and a thumbnail. A row expands in place to a full plate with a `writing-mode: vertical-lr` numeral down the edge. The spread map appears once at the top, not pinned. The benefit is that it is calm, scannable and very easy on the phone. The limit is that the spatial relationships between cards are mostly lost after the first screen.

```
  THE READING                         ┌────┐
  ───────────────────────────────────── │map │
  1  PRESENT      The Star        ▢    └────┘
  ─────────────────────────────────────
  2  CROSSING     The Tower ℞     ▢
  ───────────────────────────────────── (expands to full plate)
```

**C. Table spread (spatial-first).** This follows the Rijksmuseum and Te Papa annotated-image precedents (inferred; [Q42](https://www.q42.nl/en/work/rijksmuseum-from-home), [Springload](https://www.springload.co.nz/work/te-papa-encounters/)). The spread fills the viewport like cards laid on a table. Tapping a card zooms toward it ("pan and zoom", per the [EU data-vis guide](https://data.europa.eu/apps/data-visualisation-guide/scrollytelling-introduction)) and opens a side sheet with its explanation. The benefit is the strongest "ritual" continuity from the draw screen. The limit is that it hides the reading behind taps: linear reading becomes navigation, which is poor for screen-reader users and for skimming.

**Recommendation: A on desktop, B's row grammar on phone, and C only as the draw screen.** Concretely, do the following.

1. **Draw screen = C.** Keep `draw_screen.dart`'s full-bleed spread with the fan below. After the final reveal, a "Read the cards" button navigates to the reading. A `Hero` per placed card (tag `slot-$i`) carries each card into the reading's pinned spread. This is a legitimate route change, so Hero applies.

2. **Reading on desktop or wide layouts (≥ 900 px logical) = A.** In `reading_screen.dart`, use a `Row` with a fixed-width spread column (`SpreadLayoutView` with `slotBuilder` showing faces) and a `CustomScrollView` of explanations. Overlay a `Stack` → `IgnorePointer` → `ExcludeSemantics` → `CustomPaint(painter: LinkPainter(repaint: scrollController))`. The painter resolves `GlobalKey` render boxes, returns early for detached boxes (off-screen slivers), and draws a cubic Bézier `moveTo(a) → cubicTo(mx,a.dy, mx,b.dy, b)`. It "inks" the line with `PathMetric.extractPath(0, len * progress)` driven by a 600–700 ms controller, and sets `progress = 1` under reduced motion. Determine the active note on scroll by comparing each note's `localToGlobal().dy` with the viewport midline. Draw lines **only for the active note and its related cards**, never all ten, which keeps the overlay cheap and legible. Line colour should be ink at about 0.75 px for the active line, with gold reserved for the active slot outline, because a hairline gold line on parchment will probably fail 3:1 contrast and must not be the only carrier of the relationship.

3. **Reading on phone = B rows under a pinned strip.** Use a `CustomScrollView` with a `PinnedHeaderSliver`, which needs no size delegate ([Flutter API](https://api.flutter.dev/flutter/widgets/PinnedHeaderSliver-class.html)). It holds a compact 44 pt-high strip of numbered thumbnails, with the active one outlined. Below it sits a `SliverList` of numbered explanation rows that reuse the existing fade-in reading sections from `reading_sections.dart`. On phones, replace the long lines with a 12 px tick from the strip to the active row's number. This follows Pudding's advice to keep few steps and simplify on mobile, and to remove hover-dependent reveals on touch ([Pudding](https://pudding.cool/process/responsive-scrollytelling/)). Tapping a strip thumbnail calls `Scrollable.ensureVisible` on its row and moves focus to the row heading. Give each row `Semantics(sortKey: OrdinalSortKey(i), header: true)` so VoiceOver order matches the numerals.

4. **Shared details.** The question sits above the spread in italic serif on both layouts as the persistent reading context. Explanation headings follow "③ · Position — Card, orientation". Related cards appear as text links. The share card and constellation loader stay as they are. The AI label tag appears once, above the first section. On the future desktop web build, use CSS `position: sticky` (no scroll-jacking), the rAF-batched measure-then-write overlay (read all rects, then write all `d` attributes, re-run on `ResizeObserver` and `document.fonts.ready`), and `@supports (anchor-name: --a)` for numbered markers, with JS positioning as the fallback. Anchor positioning is listed for Chrome/Edge 125, Firefox 147 and Safari 26 ([Chrome](https://developer.chrome.com/blog/anchor-positioning-api)); re-verify support before relying on it.

*Usability tradeoff of the combination:* it costs three presentations of the same data. That is justified because each matches a task. Drawing is spatial, reading is linear, and skimming is tabular. The semantic order is identical across all three, so assistive technology meets one reading, not three.

## Conclusion

The research changes the question from "which beautiful tarot site should ShenTarot resemble?" to "which contracts make an editorial surface trustworthy?" The best references here are not mystical at all. They are an archive's grid, a literary review's numerals, a data-journalism sticky pattern and the W3C's keyboard rules. The "mystical" quality comes from restraint applied on top of them: hairline ink, gold reserved for state, and motion that only happens when something real changes. The weakest evidence is also the most glamorous, namely award sites and game feel. That is a useful warning against importing spectacle that nobody has documented.

For the existing build, the highest-leverage work is invisible. Honour iOS Reduce Motion, give the fan per-card focus, persist the question, make the shuffle loop honest, and stop the Celtic Cross crossing card from fully covering card 1. Those five fixes protect the signature interaction that is already there. The Folio reading layout is then the one genuinely new composition worth building, and the AI companion concept is worth showing only if the same honest labelling is first applied to the AI readings the app already ships.
